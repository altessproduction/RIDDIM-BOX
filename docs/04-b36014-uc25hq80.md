# B36014 — la nouvelle puce flash des FM-1 récents (UC25HQ80)

## Ce qu'est « B36014 »

Les unités M-VAVE FM-1 vendues depuis fin 2026 embarquent une puce flash SPI NOR
différente de celle des premiers lots. Elle s'identifie par son code JEDEC (lu par la
commande SPI `0x9F`) :

| JEDEC      | Puce      | Où on la trouve                          |
|------------|-----------|------------------------------------------|
| `0x856014` | Puya P25Q80 | FM-1 tels que vendus à l'origine        |
| `0xB36014` | UC25HQ80    | FM-1 vendus depuis fin 2026 (souvent AliExpress) |

Ces deux références sont documentées dans le fichier
[`sources/firmware/hal/fm1_flash_id.h`](../sources/firmware/hal/fm1_flash_id.h)
du présent dépôt : même taille (1 Mio), mêmes commandes SPI NOR
(`0x03`/`0x0B` lecture, `0x02` programmation, `0x20` effacement 4 Kio,
`0x05`/`0x35` statut, `0x06` write-enable).

## Ce que dit l'analyse du firmware communautaire RIDDIM ROOTS 0.3.0

Le binaire `RIDDIM_ROOTS_v0.3.0.fwsc` a été déballé intégralement (conteneur UFW,
`flash.bin` déchiffré, zone app déchiffrée avec la chipkey `0x980F`, chargeur
`ota.bin` extrait). Recherche effectuée dans **app.bin**, dans **l'image flash
déchiffrée** et dans **ota.bin** :

- **aucune constante JEDEC `0x856014` ni `0xB36014`** n'apparaît dans le code
  (aucun verrou « chip id » comparable au `FL_JEDEC_OK` de la lignée Felucca) ;
- le chargeur de mise à jour embarqué est le chargeur **stock JieLi**
  (`usb_hid_ota.bin` — chaînes `UPDATE_JUMP`, `POWER_PIN`, `cfg_tool`,
  `app_dir_head`, `isd_config.ini`) et ne teste pas non plus d'identifiant de puce.

**Conclusion :** le firmware 0.3.0 ne contient pas de vérification explicite
d'identifiant de flash. Sa compatibilité avec l'UC25HQ80 repose donc entièrement
sur la généricité du driver flash du SDK JieLi embarqué. Elle est **plausible mais
non garantie** : aucune unité UC25HQ80 n'était disponible pour le test, et la flash
du FM-1 est **mono-banc, sans rollback** — un firmware qui ne démarre pas sur la
puce ne peut pas être désinstallé par la machine elle-même.

## Recommandations pratiques

1. **Sur une unité à puce Puya (`0x856014`, les premiers lots)** : RIDDIM ROOTS
   0.3.0 fonctionne comme avant, rien ne change.
2. **Sur une unité à puce UC25HQ80 (`0xB36014`, fin 2026+)** : ne flashe pas 0.3.0
   sans avoir sous la main l'image stock M-VAVE officielle récente (qui gère sa
   propre puce) et l'outil M-UPGRADE, pour pouvoir revenir en arrière. Si
   possible, teste d'abord sur une machine « sacrifiable ».
3. **Le build RIDDIM ROOTS de ce dépôt (lignée Felucca/SLOOP, sources dans
   `sources/`)** déclare **explicitement les deux puces** :
   `FL_JEDEC_OK(id) ((id) == 0x856014u || (id) == 0xB36014u)` — une puce inconnue
   n'est pas endommagée : le firmware passe en mode RAM-seule (les sauvegardes ne
   persistent pas) et le chargeur de mise à jour refuse poliment. Le build
   `.fwsc` correspondant se produit avec le toolchain JieLi décrit dans
   [`sources/BUILDING.md`](../sources/BUILDING.md).

## Et l'émulateur ?

L'émulateur web de ce dépôt **n'a aucun lien avec la puce** : la flash y est
simulée en mémoire (persistance via IndexedDB du navigateur). Il exécute le même
code moteur que les sources `sources/`, quelle que soit la machine réelle.
